---
description: Define an evidence-backed objective before implementation
argument-hint: "[objective]"
---
Define the mission for ${@:-the current user objective}. This is a planning boundary, not permission to begin unrelated implementation.

1. Inspect current source and project instructions. Use a small fresh scout for unfamiliar repository structure; use a researcher only for material external unknowns. Use Astra/max for substantive work and inherited model/thinking for small delegates.
2. State the objective, writable roots, mandatory deliverables, primary success metric, non-goals, dangerous interpretations, external inputs, and canonical checks. Preserve presentations, videos, reports and other explicitly requested deliverables in the list.
3. Define at least one real CLI/API/UI journey and a relevant failure case, with observable outcomes and required artifacts. A test count is not an outcome. For experiments, define the report schema, baseline, provenance and stopping rule first.
4. Ask only for missing user-owned decisions with high rework/safety impact. Make reversible engineering decisions autonomously. Do not treat ignore/untrack as delete or permission for one repository as permission for siblings.
5. Record stable requirement IDs and pinned journeys through `workflow_contract`, using its actual latest input provenance. Preserve unfinished obligations; never fabricate a scope-change input. Link todos to requirement IDs. If the control tools are unavailable, diagnose the capability blocker rather than bypassing the contract.
6. Return the compact contract and next bounded implementation slice. Use one mission for this objective, not a new mission for every review. No CI/CD work unless requested.
